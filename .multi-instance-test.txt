PHAROS 다중 인스턴스 구현 정리
===================================

전제 조건
---------
- 인스턴스 수: 최대 3개
- Alert 규칙 수: 최대 100개
- Notification(SNMP 포함)은 이번 개발 범위에서 명시적으로 제외


이번 개발 범위
==============

1. NGINX 스티키 세션
--------------------
목적: 리프레시 토큰/세션 연속성, 웹소켓 연결 안정성 확보

구현:
- 쿠키 기반 스티키 라우팅 설정 (NGINX ip_hash 또는 sticky cookie)
- 인스턴스가 죽으면 NGINX가 정상 인스턴스로 페일오버
- 페일오버 시 해당 사용자는 재로그인 필요 (허용 가능한 트레이드오프)

한계 (수용):
- 다른 인스턴스에서 발생한 웹소켓 이벤트는 전달되지 않음 → 폴링으로 보완


2. 공유 JWT 키/시크릿 설정
--------------------------
목적: 인스턴스 간 액세스 토큰 교차 검증 허용

구현:
- 모든 인스턴스가 동일한 JWT 서명 키/인증서를 사용하도록 설정
- 모든 인스턴스가 동일한 인증 글로벌 시크릿을 공유
- 리프레시 토큰은 여전히 프로세스 로컬 (스티키 세션으로 보완)


3. Alert 규칙 주기적 DB 동기화
------------------------------
목적: 런타임 규칙 변경(생성/수정/삭제)이 모든 인스턴스에 반영되도록 함

현재 문제:
- 인스턴스 A에서 규칙을 변경하면 A의 로컬 크론만 업데이트됨
- B/C는 재시작 전까지 변경을 인지하지 못함

구현:
- 모든 인스턴스에 주기적 DB 동기화 루프 추가
- 각 인스턴스가 주기적으로 `alert_rule` 테이블을 읽음
- `rule_id` + `updated_at`(또는 규칙 JSON 해시)로 로컬 크론과 비교
- 누락 규칙 추가 / 변경 규칙 재스케줄 / 삭제 규칙 제거

참고:
- 규칙은 모든 인스턴스에서 실행됨 (DB 리스 없음)
- 최대 3인스턴스 × 100규칙 = 300 쿼리/사이클로 허용 가능한 수준


4. history_alert_row 중복 방지
------------------------------
목적: 여러 인스턴스가 동일한 전환을 처리할 때 히스토리 행 중복 방지

현재 문제:
- `history_alert_row`는 append-only라 중복 삽입 시 중복 행 발생
- `history_alert`는 upsert로 수렴되므로 문제 없음

구현:
- `history_alert_row`에 unique constraint 추가
  예: UNIQUE (alert_id, transitioned_at) 또는
      UNIQUE (alert_id, from_state, to_state, transitioned_at)
- INSERT 시 ON CONFLICT DO NOTHING 처리
- 코드 변경 없이 DB 레벨에서 중복 차단


5. 프론트엔드 폴링 폴백
-----------------------
목적: 웹소켓 이벤트 누락 시 UI가 자동으로 DB 상태를 반영하도록 함

구현:
- 웹소켓은 베스트 에포트로 유지, 폴링을 신뢰 원천으로 사용
- 폴링 대상 및 주기:
  - 활성 Alert 상태 (`/alert/status`): 10~30초마다
  - 규칙 상세/상태 뷰 (`/alert/rule?detail=true`): 탭 진입 시 + 필요 시
  - 히스토리 (`/alert/hist`): 탭 진입 시 + 30~60초마다


이번 범위 제외 항목
===================

Notification (SNMP 포함)
- 현재 실제 구현된 알림 수단은 SNMP뿐
- SNMP를 사용하지 않는 환경에서는 중복 발송 문제가 실질적으로 없음
- 현재 규모(3인스턴스 / 100규칙)에서 허용 가능한 트레이드오프로 판단
- 향후 DB 리스 도입 시 함께 해결

규칙 단위 DB 리스
- 현재 규모에서 구현 복잡도 대비 효과 미미
- Notification 중복 문제가 실질적으로 없는 상황에서 우선순위 낮음
- 인스턴스 수 증가 또는 Notification 활성화 시 도입

공유 세션/리프레시 토큰 저장소 (DB/Redis)
- 스티키 세션으로 충분히 보완 가능
- 페일오버 시 재로그인은 허용 가능한 수준으로 판단

웹소켓 백플레인 (NATS/Redis/Centrifuge)
- 폴링 폴백으로 커버 가능
- 실시간 전달 보장이 요구사항으로 확정되면 도입


향후 과제 (이번 이후)
=====================

1. 규칙 단위 DB 리스
   - 인스턴스 수 증가 또는 Notification 활성화 시 도입
   - 중복 쿼리, 히스토리 행, Notification 전송 동시 해결

2. 공유 세션 저장소
   - 리프레시 토큰/세션을 DB 또는 Redis로 이동
   - 페일오버 시 재로그인 불필요

3. 웹소켓 백플레인
   - 실시간 전달 보장이 필요할 경우 도입
   - 폴링은 폴백으로 유지

# 권한 관리 설계 가이드

## 1. 단순 역할(Role) 기반
**방식**
- 사람에게 “역할” 하나만 부여
- 예: **관리자(Admin)**, **일반 사용자(User)**

**장점**
- 이해하기 쉽고 단순
- 작은 서비스나 내부 관리 툴에 적합
- 기획/디자인에서 고민할 게 적음
    - 예: “관리자는 모든 메뉴, 사용자는 제한된 메뉴”

**단점**
- 중간 단계의 권한을 주기 어려움
    - 예: “글은 작성할 수 있지만 삭제는 못 한다” 같은 세부 권한 설정 불가
- 서비스가 커지면 결국 세분화 필요

---

## 2. 역할(Role) + 권한(Permission) 기반
**방식**
- “역할(Role)”은 그룹 개념
- 실제 행동은 “권한(Permission)”으로 정의

**예시**
- **관리자(Admin)** → 모든 권한
- **에디터(Editor)** → 글 작성/수정 가능, 삭제 불가
- **뷰어(Viewer)** → 읽기만 가능

**장점**
- 서비스가 커져도 유연하게 대응 가능
- 버튼, 메뉴, 기능 노출 여부를 세밀하게 제어 가능
- SaaS 서비스처럼 다양한 고객 환경에서도 확장 가능

**단점**
- 구조가 복잡해짐

---

## 3. 현실적인 접근
- 작은 서비스나 내부 툴 → **단순 Role 기반**으로 시작 (Admin/User 정도)
- 서비스 확장 시 → **Role과 Permission을 매핑하는 구조**로 확장
- 즉, **처음에는 단순하게 시작**하고, 필요해지면 **세분화된 권한 모델**을 도입하는 게 일반적
- 다만, 자사 서비스는 요구사항이 빈번하게 변경되기 때문에 유연성이 중요

---

## 4. UI/디자인 관점에서의 적용
- **Role 기반만 사용하는 경우**
    - 관리자: 모든 버튼/메뉴 보임
    - 사용자: 일부 버튼/메뉴 숨김

- **Permission 기반까지 가는 경우**
    - API에서 내려준 권한 목록을 보고
        - “이 버튼은 보여줄지, 숨길지”
        - “이 메뉴는 클릭 가능할지, 비활성화할지”
    - 를 제어

---

## 결론
- 초기에는 **Admin/User 같은 단순 Role 관리**가 직관적이고 빠름
- 서비스가 커지면 **Permission 기반으로 확장**하는 게 안전하고 유연
**- UI/디자인은 “권한에 따라 보이는 요소가 달라진다”는 원칙만 알면 됨**
- 보안은 항상 **백엔드에서 최종 검증**이 필요  
- 자사 프로젝트는 초기 설계되면 중간에 되돌리기 힘들기 때문에 초반에 유연성 확보 필요

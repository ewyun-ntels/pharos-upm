# Dashboard Query Build - Grafana vs Pharos 비교 및 멀티 스타일 설계

작성일: 2026-05-21

---

## 1. 워크플로우 비교

### 공통점
- 대시보드에 쿼리(템플릿)를 등록
- 변수(Variables)를 통해 동적으로 쿼리 값을 치환
- 데이터소스 타입별로 쿼리 실행 방식이 다름

### 핵심 차이: 치환 위치

```
[Grafana]
  Frontend
    └─ template_srv.ts → $variable, ${var:format}, [[var]] 치환
         ↓ (치환 완료된 쿼리를 백엔드로 전송)
  Backend
    └─ 1단계: 글로벌 매크로 치환 ($__interval_ms, $__unixEpochFrom() 등)
    └─ 2단계: 데이터소스별 매크로 치환 ($__timeFilter(col), $__table 등)
    └─ 최종 쿼리 실행

[Pharos]
  Frontend
    └─ 변수값(variables)만 백엔드로 전달 (쿼리 문자열은 템플릿 그대로)
         ↓
  Backend
    └─ convertInternalContext() → __start_time, __end_time 등 시간 변수 변환
    └─ pongo2.FromString() → {{ variable }} 치환
    └─ 데이터소스 타입별 실행 (Prometheus / Elasticsearch / SQL)
```

---

## 2. Grafana 변수 문법 (template_srv.ts)

정규식: `/\$(\w+)|\[\[(\w+?)(?::(\w+))?\]\]|\${(\w+)(?:\.([^:^\}]+))?(?::([^\}]+))?}/g`

| 문법 | 예시 | 설명 |
|------|------|------|
| `$varName` | `$host` | 단순 변수 |
| `[[varName]]` | `[[host]]` | 레거시 문법 |
| `${varName}` | `${host}` | 확장 문법 |
| `${varName:format}` | `${hosts:csv}` | 포맷 지정 |

포맷 종류: `csv`, `regex`, `json`, `text`, `glob` 등

Grafana 특수 매크로 (백엔드 처리):
- `$__interval` / `$__interval_ms` — 쿼리 인터벌
- `$__timeFilter(column)` — WHERE 시간 조건 자동 생성
- `$__unixEpochFrom()` / `$__unixEpochTo()` — Unix timestamp
- `$__table` — 테이블명
- `$__from` / `$__to` — 시간 범위

## 3. Pharos 현재 구조

### 핵심 파일
- `core/internal/query_builder/template.go` — pongo2 치환 로직
- `core/internal/query_builder/query_spec.go` — QuerySpec 구조체
- `core/pkg/dashboard/handler/query.go` — 쿼리 핸들러
- `core/pkg/plugins/ds_query_response.go` — 데이터소스별 쿼리 실행

### 치환 흐름 (template.go)
```go
func GetQuery(query string, queryContext map[string]any) ([]byte, error) {
    convertContext, _ := convertInternalContext(queryContext)
    // 특수 시간 변수 변환:
    //   __start_time    → Unix timestamp (초)
    //   __end_time      → Unix timestamp (초)
    //   __start_time_ms → Unix timestamp (밀리초)
    //   __end_time_ms   → Unix timestamp (밀리초)

    tpl, _ := pongo2.FromString(query)
    out, _ := tpl.Execute(convertContext)
    return []byte(out), nil
}
```

### 데이터소스 타입별 분기 (config.go)
| 타입 | 처리 함수 |
|------|----------|
| Prometheus | `makeDatabaseResponseForPrometheus()` |
| Elasticsearch | `makeDatabaseResponseForElasticsearch()` |
| ClickHouse / PostgreSQL / Altibase / Vertica | `makeDatabaseResponseForSqlx()` |

## 4. 멀티 스타일 쿼리 빌더 설계

### 목표
쿼리 등록 시 템플릿 스타일을 지정해 빌드 방식을 분기한다.
- `"pongo2"` 스타일: 현재 방식 유지 (`{{ variable }}`)
- `"grafana"` 스타일: Grafana 문법 지원 (`$variable`, `${var:format}`)

### 파일 구조 변경
```
core/internal/query_builder/
  template.go      ← 기존 pongo2 로직 (유지)
  grafana.go       ← 신규: Grafana 스타일 치환
  builder.go       ← 신규: 스타일 디스패처
  query_spec.go    ← Style 타입 추가
```

### builder.go (디스패처)
```go
type Style string

const (
    StylePongo2  Style = "pongo2"
    StyleGrafana Style = "grafana"
)

func Build(style Style, query string, ctx map[string]any) ([]byte, error) {
    switch style {
    case StyleGrafana:
        return buildGrafana(query, ctx)
    default: // StylePongo2 또는 미지정
        return GetQuery(query, ctx)
    }
}
```

### grafana.go (Grafana 스타일 치환)
처리 대상:
```
$varName          → context["varName"] 값으로 치환
${varName}        → 동일
${varName:csv}    → 값이 배열일 경우 콤마 구분 문자열
${varName:regex}  → regex-safe 이스케이프
${varName:json}   → JSON 인코딩
$__start_time     → __start_time 처리 (기존 로직 재사용)
$__end_time       → __end_time 처리 (기존 로직 재사용)
```

### 변경 필요 파일
1. `shared/types/dashboard/types.go`
   - `ChartQuery` 구조체에 `TemplateStyle string` 필드 추가

2. `core/pkg/dashboard/handler/query.go`
   - `Run` 구조체에 `TemplateStyle string` 추가
   - `getPostResponse()` 에서 `query_builder.GetQuery()` 대신 `query_builder.Build()` 호출

3. `core/internal/query_builder/builder.go` (신규)
   - Style 타입 및 Build() 함수

4. `core/internal/query_builder/grafana.go` (신규)
   - Grafana 문법 regex 치환 구현

### 호출 예시 (변경 후 query.go)
```go
func (query *Query) getPostResponse(ctx context.Context) (int, orm.DatabaseResponse, error) {
    style := query_builder.Style(query.Run.TemplateStyle)
    sql, err := query_builder.Build(style, query.Run.Query, query.Variables)
    // ...
}
```

## 5. 미결 사항 (구현 전 확인 필요)

1. **스타일 저장 위치**
   - ChartQuery(대시보드 설정에 영구 저장) — 권장
   - 요청 바디에서 매번 전달 — 간단하지만 비일관적

2. **Grafana 포맷 지원 범위**
   - 단순 치환만 (`$var` → 값)
   - 포맷팅 포함 (`${var:csv}`, `${var:regex}`, `${var:json}`)

3. **default 스타일**
   - 미지정 시 `pongo2`를 default로 유지 (하위 호환)

## 6. 리뷰 피드백 검토 및 추가 의견 (2차 보완 포함)

### [검증 완료] High: TemplateStyle 전파 지점 부족

코드를 직접 확인한 결과 지적이 정확합니다.

**누락 지점 1 — panelToRun() (query.go:297-302)**
```go
// 현재: DatasourceName, Query만 복사
query.Run.DatasourceName = chartQuery.DatasourceName
query.Run.Query = chartQuery.Query
// → TemplateStyle 복사 없음. 수정 필요.
```

**누락 지점 2 — getInspectResponse() (query.go:109)**
```go
// 현재
executedSQL, err := query_builder.GetQuery(query.Run.Query, query.Variables)
// → GetQuery() 직접 호출. Build()로 교체 필요.
```

`getPostResponse()`와 `getInspectResponse()` 모두 `Build()`로 교체하지 않으면
inspect 결과와 실제 실행 결과가 다른 엔진으로 치환되어 디버깅 불일치가 발생합니다.

### [검증 완료] Medium: 타입 추가는 Go만으로 끝나지 않음 — 위험도 상향 권장

설계서에서 `types.go`만 언급했지만 실제 수정 지점은 네 곳입니다.

| 파일 | 역할 | 누락 시 증상 |
|------|------|------------|
| `shared/schema/dashboard/ChartQuery.schema` | JSON Schema (원본) | RJSF 폼에서 검증 오류 / quicktype 재생성 시 필드 누락 |
| `shared/types/dashboard/types.go` | Go 구조체 (generated) | 백엔드 역직렬화 실패 |
| `shared/frontend/src/types/dashboard/index.ts` | Zod Schema (generated) | Zod `z.object()` 파싱 시 unknown 키 silently strip |
| `core/frontend/src/types/charts.ts` | 로컬 프론트 타입 | ChartQuery 확장 타입에서 필드 누락 |

`types.go`와 `index.ts`는 generated 파일입니다. 직접 수정하면 다음 quicktype 재생성 시 덮어써집니다.
반드시 `ChartQuery.schema` 수정 → quicktype 스크립트 실행 → 자동 재생성 순서로 진행해야 합니다.

동작 차이:
- `ChartQuery.schema`의 `additionalProperties: false` → RJSF 기반 폼에서 **검증 오류** 유발
- Zod `z.object()` 기본 동작 → unknown 키를 **silently strip** (에러 없이 제거)

두 경로 모두 `templateStyle`을 schema에 먼저 추가해야 막을 수 있습니다.

**권장 조치:** `ChartQuery.schema` 수정 → quicktype 재생성을 가장 먼저 실행.

### [동의] High: Grafana 포맷 안전성

`${var:sqlstring}` 미구현 시 아래와 같은 문제가 생깁니다.

```sql
-- 사용자 입력 예: $hostname = "server'; DROP TABLE metrics; --"
-- 단순 치환 결과
SELECT * FROM metrics WHERE host = 'server'; DROP TABLE metrics; --'
```

**구현 우선순위 (보안 중요도 기준):**

| 포맷 | 출력 예시 (값: `["a","b"]`) | 용도 |
|------|--------------------------|------|
| (미지정, glob 기본값) | `{a,b}` | Grafana 기본값. multi-value는 `{a,b}` 형태로 출력해야 호환됨 |
| `raw` | `a,b` | 변환 없음 |
| `csv` | `a,b` | 콤마 구분, quoting 없음 |
| `singlequote` | `'a','b'` | SQL IN 절 리터럴 |
| `sqlstring` | `'a','b'` | SQL single quote escape (`a'b` → `'a''b'`) — **injection 방지 필수** |
| `regex` | `(a|b)` | PromQL/regex 다중값. 값 내 메타문자 escape. 예: `(test\.|test2)` |
| `json` | `["a","b"]` | Elasticsearch body |

미구현 포맷을 요청하면 `${var:unknownformat}` 문자열이 그대로 원본 유지됩니다 (Pharos 정책).
→ 9번 섹션 최종 정책 참고. (Grafana는 glob fallback, Pharos는 원본 유지로 다름)

---

### [동의 + 범위 제안] Medium: 시간 변수 alias 정책

Grafana의 `${__from}` / `${__to}` 는 밀리초 epoch이고,
Pharos의 `__start_time` / `__end_time` 은 초 epoch입니다.
단위가 다르므로 단순 alias는 오동작을 유발합니다.

**권장 mapping:**

| Grafana 변수 | Pharos 대응 | 단위 |
|-------------|------------|------|
| `$__from` / `${__from}` | `__start_time_ms` | 밀리초 |
| `$__to` / `${__to}` | `__end_time_ms` | 밀리초 |
| `${__from:date:seconds}` | `__start_time` | 초 |
| `${__to:date:seconds}` | `__end_time` | 초 |
| `$__interval_ms` | 미지원 (범위 외) — 단, 11-A에서 1차 포함 여부 최종 결정 | — |

`convertInternalContext()`는 이미 `_ms` suffix 처리 로직이 있으므로
Grafana 스타일 빌더에서 `__from` / `__to` 를 각각 `__start_time_ms` / `__end_time_ms`로
rename 후 동일 함수에 넘기는 방식으로 재사용할 수 있습니다.

---

### [범위 제안] Medium: 데이터소스별 매크로 분리

`$__timeFilter(column)` 같은 함수형 매크로는 첫 버전에서 제외를 권장합니다.

**이유:**
- 매크로가 생성하는 SQL은 데이터소스 방언에 따라 다릅니다.
  - PostgreSQL: `"column" BETWEEN '...' AND '...'`
  - ClickHouse: `column >= toDateTime(...) AND column <= toDateTime(...)`
- 지원하려면 빌더가 타겟 데이터소스 타입을 알아야 하므로
  현재 `Build(style, query, ctx)` 시그니처를 `Build(style, dsType, query, ctx)`로 확장해야 합니다.
- 이 확장을 나중에 추가하더라도 기존 코드에 영향이 없도록
  지금부터 `datasourceType` 파라미터를 optional로 받는 구조로 설계하는 것을 권장합니다.

**현실적인 1차 범위:**
```
포함: $var, ${var}, [[var]], 포맷 7종 (glob기본값/raw/csv/singlequote/sqlstring/regex/json), 시간 변수 alias
제외: $__timeFilter(), $__timeGroup(), $__table, $__interval, $__interval_ms
      (단, $__interval/$__interval_ms/$__step는 11-A에서 1차 포함 여부 최종 결정 — 프론트 variables에 값 주입으로 해결 가능)
```

### [정정] Medium: JSON Schema 동작 설명 수정

이전 섹션에서 "additionalProperties: false로 인해 필드가 저장 시 자동으로 제거됨"이라고 적었는데
표현이 부정확합니다.

**정확한 동작:**
- `ChartQuery.schema`의 `additionalProperties: false`는 JSON Schema **검증 실패**를 유발합니다.
- 조용히 필드가 사라지는 것은 `shared/frontend/src/types/dashboard/index.ts:79`의
  Zod `z.object()` 파싱 기본 동작입니다. Zod는 unknown 키를 기본으로 **strip(제거)** 합니다.
  (`z.object().passthrough()`를 써야 보존됩니다.)

따라서 실제 위험 경로는:
- JSON Schema → RJSF 기반 폼에서 사용 시 검증 오류
- Zod → 프론트 저장/로드 파싱 시 silently strip

두 경로 모두 `templateStyle`을 추가해야 막을 수 있다는 결론은 동일합니다.

### [정정] Medium: Grafana 포맷 기본값, csv, regex 동작

이전 섹션에 세 가지 오류가 있었습니다.

**오류 1: 기본 포맷**
- 이전 표현: `raw` (포맷 미지정 fallback)
- 정정: Grafana의 포맷 미지정 기본값은 **`glob`** 입니다. (`formatVariableValue.ts:29`)
- Pharos 구현 시 미지정 multi-value는 `{a,b}` 형태로 출력해야 Grafana 호환됩니다.

**오류 2: csv 포맷 출력**
- 이전 표현: `'a','b','c'`
- 정정: `csv` 포맷 출력은 **`a,b,c`** 입니다. (quoting 없음)
- quoting이 필요한 것은 `singlequote`(`'a','b','c'`) 또는 `sqlstring` 역할입니다.

**오류 3: regex 포맷 예시**
- 이전 표현: `a\|b\|c` (값 안에 pipe가 있는 것처럼 읽힘)
- 정정: Grafana multi-value regex는 값들을 `|`로 묶어 **`(a|b)`** 형태로 출력합니다.
  값 자체가 `.` 같은 regex 메타문자를 포함하면 escape합니다. 예: `(test\.|test2)`
- 앞 표의 `regex` 행도 `(a|b)` 기준으로 통일합니다.

### [사용자 요구사항] 쿼리창 grafanaStyle switch

쿼리 편집 UI에는 selector/dropdown이 아니라 `grafanaStyle` switch를 둡니다. 사용자가 이 switch를 켜면 해당 쿼리는 Grafana 스타일로 동작해야 합니다.

권장 모델:

| UI | 저장/전송 값 | 동작 |
|----|-------------|------|
| `grafanaStyle = false` | `templateStyle: "pongo2"` | 기존 pongo2 `{{ variable }}` 방식 |
| `grafanaStyle = true` | `templateStyle: "grafana"` | Grafana `$var`, `${var:format}`, `[[var]]` 방식 |

구현 기준:
- UI control 이름/라벨은 `grafanaStyle` switch로 둡니다.
- 스키마와 백엔드/요청 전파 필드는 기존 설계대로 `templateStyle`을 사용합니다.
- 즉, `grafanaStyle`은 UI boolean이고, 저장/전송 시 `templateStyle`로 매핑합니다.
- switch는 query별 설정입니다. 여러 query가 있는 패널에서는 각 query마다 독립적으로 켜고 끌 수 있어야 합니다.
- 새 query의 기본값은 `grafanaStyle = false`, `templateStyle = "pongo2"`로 둡니다.
- 기존 저장 데이터처럼 `templateStyle`이 없는 경우만 백엔드에서 `"pongo2"`로 fallback합니다.
- 저장된 `templateStyle: "grafana"` query를 에디터에서 다시 열면 switch가 ON 상태로 복원되어야 합니다.

### [사용자 요구사항] 디버깅용 상세 로그 추가

로그 원칙:

| unsupported format | debug 또는 warn | var name, format, 원본 유지 사유 (`unsupported format`) |
| field path 감지 | debug | var name, field path, 원본 유지 사유 (`field path unsupported`) |
| `getPostResponse()` | debug | datasourceName, templateStyle, timeout, inspect 여부 |
| `getInspectResponse()` | debug | raw/executed query length, templateStyle |

```go
slog.Debug("Grafana variable interpolation",
```

### [추가 Medium] unsupported format 정책은 Grafana와 다름

실제 Grafana의 `formatVariableValue.ts`는 알 수 없는 format이 들어오면 에러를 던지지 않고 `glob`으로 fallback합니다.

```typescript
if (!formatItem) {
  console.error(`Variable format ${format} not found. Using glob format as fallback.`);
  formatItem = formatRegistry.get(VariableFormatID.Glob);
}
```

따라서 최종 정책은 Grafana와 달리 unsupported format을 원본 유지하는 방식으로 통일합니다.

권장 정책:
- `format`이 명시됐고 지원하지 않는 값이면 원본 토큰 유지 (Pharos 정책 — Grafana는 glob fallback)
- `format`이 미지정이면 Grafana와 동일하게 `glob` 적용
- 이 정책은 "Grafana 문법 기반의 Pharos-safe subset"이라고 문서화합니다.

테스트 케이스:
```go
// unsupported format: 원본 유지 (Pharos 정책 — Grafana는 glob fallback으로 다름)
${host:unknownformat} with ctx["host"] exists -> ${host:unknownformat} (unchanged)

// omitted format: glob 기본값
${hosts} with ["a", "b"] -> {a,b}
```

### [추가 High] context map을 변수 whitelist로 사용

Grafana 스타일 빌더는 별도 whitelist 구조를 만들 필요 없이 `variables`/`ctx` map 자체를 whitelist로 사용하면 됩니다.

백엔드 요청 구조:
```json
{
  "run": {
    "query": "...",
    "datasourceName": "..."
  },
  "variables": {
    "job": "production",
    "pod": "tcp-bridge-1",
    "sys_id": "sys-001",
    "__start_time": 1700000000,
    "__end_time": 1700003600
  }
}
```

정책:
```go
func buildGrafana(query string, ctx map[string]any) ([]byte, error) {
    result := grafanaVariableRegex.ReplaceAllStringFunc(query, func(match string) string {
        varName, format := extractGrafanaVariable(match)

        val, exists := ctx[varName]
        if !exists {
            return match // context에 없는 변수는 원본 토큰 유지
        }

        return formatGrafanaVariable(val, format)
    })

    return []byte(result), nil
}
```

이 정책은 Grafana의 `template_srv.ts` 동작과도 맞습니다. Grafana도 변수 레지스트리에 없는 이름은 원본 match를 반환합니다.

중요 효과:

| 입력 토큰 | context 조회 | 결과 |
|----------|--------------|------|
| `$job` | `ctx["job"]` 존재 | 선택값으로 치환 |
| `$pod` | `ctx["pod"]` 존재 | 선택값으로 치환 |
| `$1` | `ctx["1"]` 없음 | `$1` 원본 유지 |
| `$__unknown` | 대응 context/alias 없음 | 원본 유지 |

따라서 Prometheus `label_replace()`의 capture group인 `$1`은 별도 예외 처리 없이 안전하게 보존됩니다.

예:
```promql
label_replace(metric, "sys_id", "$1", "pod", ".*(tcp-bridge-[0-9]+).*")
```

위 쿼리에서 `$1`은 `ctx["1"]`이 없으므로 원본 그대로 남고, PromQL capture group으로 정상 동작합니다.

단, `ctx에 없으면 원본 유지`는 missing variable 보존 정책이지 unsupported format 정책과는 별개입니다.

권장 에러 정책:
- 변수명이 context에 없음 → 원본 토큰 유지
- 변수명은 context에 있지만 명시 format이 미지원 → 원본 토큰 유지
- format 미지정 → 지원 정책에 따라 기본 `glob` 적용

테스트 케이스:
```go
// known variable
`up{job=~"$job"}` with ctx["job"] = "production"
=> `up{job=~"production"}`

// Prometheus capture group must be preserved
`label_replace(metric, "sys_id", "$1", "pod", ".*(tcp-bridge-[0-9]+).*")`
=> unchanged `$1`

// missing dashboard variable must be preserved
`up{job=~"$missing"}`
=> `up{job=~"$missing"}`

// known variable + unsupported explicit format must be preserved
`${job:unknownformat}` with ctx["job"] exists
=> `${job:unknownformat}`
```

### [추가 Medium] PromQL 다중값은 `$var` 보존 정책과 별개

`$1` 오치환 문제는 context whitelist 정책으로 해결됩니다. 하지만 PromQL regex matcher에서 다중값 변수를 어떻게 표현할지는 별도 문제입니다.

예:
```promql
{job=~"$job"}
```

`job`이 단일값이면 문제 없습니다.
```text
ctx["job"] = "job1"
{job=~"job1"}
```

하지만 `job`이 다중값이면 format 미지정 기본값에 따라 PromQL에 맞지 않는 결과가 나올 수 있습니다.
```text
ctx["job"] = ["job1", "job2"]

// glob 기본값이면 PromQL regex로는 부적절
{job=~"{job1,job2}"}
```

PromQL regex matcher에서는 쿼리 작성자가 명시적으로 `regex` format을 사용하는 것을 권장합니다.
```promql
{job=~"${job:regex}"}
```

예상 결과:
```text
{job=~"(job1|job2)"}
```

정리:

| 문제 | 해결 방법 |
|------|----------|
| `$1` 오치환 | context map을 whitelist로 사용하고, 없으면 원본 유지 |
| PromQL 다중값 | 쿼리 작성 시 `${var:regex}` 명시 |

1차 구현에서는 `$var`를 datasource별로 암묵 변환하지 않는 것이 안전합니다. 즉, `job=~"$job"`에서 다중값을 자동 regex로 바꾸는 정책은 피하고, `${job:regex}`처럼 쿼리 안에서 format을 명시하도록 안내합니다.

---

### [추가 Medium] singlequote / sqlstring 차이 명확화 필요

Grafana 테스트 기준으로 `singlequote`와 `sqlstring`은 둘 다 작은따옴표로 감싸지만 escape 방식이 다릅니다.

| 포맷 | 입력 | 출력 | 비고 |
|------|------|------|------|
| `singlequote` | `test'2` | `'test\'2'` | backslash escape |
| `sqlstring` | `test'value` | `'test''value'` | SQL 표준 quote escape |

SQL 쿼리에서는 `sqlstring`을 기본 권장해야 합니다. `singlequote`는 Grafana 호환용 포맷으로 지원하되, SQL injection 방어 목적의 주 포맷으로 설명하면 안 됩니다.

## 9. "미지원 변수 없음" 정책 확정 (2026-05-21)

### 결론

`[추가 High] context map을 변수 whitelist로 사용` 정책을 채택하면,
기존 문서의 "미지원 변수 목록"은 사실상 무의미해집니다.

모든 패턴에 대한 동작은 아래 네 가지로 단순화됩니다.

| 경우 | 동작 |
|------|------|
| context에 있는 변수 | 값으로 치환 |
| context에 없는 변수 (`$1`, `$__unknown` 등) | 원본 토큰 유지 (통과) |
| 변수는 context에 있으나 명시 format이 미지원 | 원본 토큰 유지 (Pharos 정책 — Grafana는 glob fallback으로 다름) |
| format 미지정 | glob 기본값 적용 (`{a,b}`) |

따라서 `$__timeFilter`, `$__table` 등은 context에 없으므로 빌더는 원본 그대로 전달합니다.
`$__interval`, `$__interval_ms`는 프론트에서 variables에 주입하면 치환되고,
주입하지 않으면 마찬가지로 원본 유지됩니다 (11-A 참고).
해당 datasource가 이 패턴을 이해하지 못하면 실행 단계에서 오류가 발생합니다 (빌더 레벨 오류가 아님).

---

### 예외 1: `${__from:date}`, `${__from:date:YYYY-MM}`

이 패턴은 `__from` 변수에 `date` format을 명시한 형태입니다.
구현 방식에 따라 동작이 달라지므로 반드시 **구현 B**를 채택해야 합니다.

**구현 A — `__from`을 context에 직접 넣는 경우 (채택 금지)**
```
${__from:date}         → ctx["__from"] 존재 → format "date" 미지원 → 원본 유지 (OK)
${__from:date:seconds} → ctx["__from"] 존재 → format "date:seconds" 미지원 → 원본 유지 ❌
                         (seconds alias가 동작하지 않음 — 채택 금지 이유)
```

**구현 B — `__from`을 context에 넣지 않고 특정 alias 패턴만 pre-process (채택)**
```
${__from:date:seconds} → 1단계 pre-process에서 ctx["__start_time"] 치환 ✅
${__from:date}         → 1단계 미매칭 → 2단계 ctx["__from"] 없음 → 원본 유지 ✅
$__from / ${__from}    → 1단계 pre-process에서 ctx["__start_time_ms"] 치환 ✅
```

**구현 B 핵심 제약: ctx에 `__from`, `__to` 키를 절대 추가하지 말 것.**
`convertInternalContext()`나 alias 매핑 함수가 `__from`/`__to` 키를 ctx에 넣으면
구현 A의 문제가 그대로 재현됩니다.

권장 구현 구조:

```go
func buildGrafana(query string, ctx map[string]any) ([]byte, error) {
    // 1단계: 지원하는 시간 alias 패턴을 정규식보다 먼저 처리
    //   ${__from:date:seconds} → ctx["__start_time"]
    //   ${__to:date:seconds}   → ctx["__end_time"]
    //   $__from / ${__from}    → ctx["__start_time_ms"]
    //   $__to   / ${__to}      → ctx["__end_time_ms"]
    query = replaceTimeAliases(query, ctx)

    // 2단계: 일반 변수 치환 (context whitelist)
    result := grafanaRegex.ReplaceAllStringFunc(query, func(match string) string {
        varName, _, format := extractGrafanaVariable(match)
        val, exists := ctx[varName]
        if !exists {
            return match // 원본 유지
        }
        return formatGrafanaVariable(val, format)
    })

    return []byte(result), nil
}
```

이 구조에서 `${__from:date}`는 1단계 미매칭 → 2단계 ctx 없음 → 원본 유지로
오류 없이 통과합니다.

---

### 예외 2: `${var.field}` field path

Grafana 정규식은 field path를 별도 캡처그룹으로 처리합니다.

```
\${(\w+)(?:\.([^:^\}]+))?(?::([^\}]+))?}
         ↑        ↑
       varName   field (optional)
```

`${server.host}` → varName=`server`, field=`host`

field path는 1차 범위에서 지원하지 않습니다.
`field != ""`이면 varName이 context에 있더라도 무조건 원본 유지합니다.
(field를 무시하고 varName만 조회하면 `${server.host}`가 server 전체 값으로 오치환됩니다.)

```go
varName, field, format := extractGrafanaVariable(match)

// field path는 미지원: field가 있으면 원본 반환
if field != "" {
    return match
}

val, exists := ctx[varName]
if !exists {
    return match // 원본 유지
}
```

`${server.host}` → field="host" != "" → 원본 유지 → 통과.
`${server}` → field="" → ctx["server"] 조회 → 정상 치환.

### 기존 "1차 미지원 문법 목록" 섹션 수정

`[추가 Medium] 1차 미지원 문법 목록 명시` 섹션의 "미지원" 표현은
context whitelist 정책과 충돌합니다.

올바른 표현으로 수정:

| 문법 | 예시 | 동작 |
|------|------|------|
| field path | `${var.field}` | field != "" → 무조건 원본 유지 (varName 조회 안 함) |
| date ISO/custom | `${__from:date}`, `${__from:date:YYYY-MM}` | 구현 B 채택 시 ctx["__from"] 없음 → 원본 유지 |
| datasource macro | `$__timeFilter(ts)`, `$__timeGroup(ts, '5m')` | ctx["__timeFilter"] 없음 → 원본 유지 |
| interval macro | `$__interval`, `$__interval_ms` | 프론트 variables 미주입 시 ctx 없음 → 원본 유지 (11-A 참고) |
| table macro | `$__table` | ctx 없음 → 원본 유지 |

이 패턴들은 "미지원 → 원본 통과"입니다.
단, `$__interval`, `$__interval_ms`는 프론트 variables 미주입 시에만 원본 통과이며,
주입하면 일반 변수와 동일하게 치환됩니다 (11-A 참고).
빌더 레벨 오류는 발생하지 않으며, datasource가 해석하지 못하면 실행 단계에서 오류가 납니다.

## 10. Alert rule Grafana 스타일 지원 — 1차 제외, 2차 고려사항 (2026-05-21)

### 1차 범위 확정: Alert rule은 pongo2 유지

Alert rule의 Grafana 스타일 지원은 1차 구현 범위에서 명시적으로 제외합니다.

**제외 근거:**

1. **UI 구조가 다름**
   Alert 등록 화면에는 대시보드의 VariableBar 같은 변수 정의/선택 UI가 없습니다.
   현재 화면 구성: `Datasource`, `Query`, `Time Label`, `Variable Label`, `Evaluation Interval`, `Check Type`
   → 사용자가 `$job`, `$pod` 같은 변수를 등록하거나 선택하는 경로 자체가 없습니다.

2. **설계 패턴이 다름**
   Alert rule의 `Datasource` 구조체 자체가 "특정 컬럼에서 scalar 값 추출 → 임계값 비교"의 고정 패턴입니다.
   ```go
   type Datasource struct {
       Variables     map[string]any  // UI에서 채울 경로 없음
       Query         string
       TimeLabel     string          // 정적: 시간 컬럼명
       VariableLabel string          // 정적: 값 컬럼명
   }
   ```
   대시보드처럼 "사용자가 필터를 선택 → 쿼리가 달라짐"이 아니라
   "등록된 쿼리 → 고정 컬럼 → 임계값 비교"가 alert 실행 단위입니다.

3. **백그라운드 스케줄러 실행**
   대시보드 변수는 사용자 화면 상태/세션 상태에 묶입니다.
   Alert rule은 사용자가 화면을 보지 않아도 cron으로 계속 실행되므로
   대시보드 변수 시스템과 자연스럽게 맞지 않습니다.

4. **반쪽 구현 위험**
   Grafana 스타일만 넣고 저장 포맷과 스케줄러를 그대로 두면
   rule 등록 → 저장 → 스케줄 실행 전 경로가 불일치합니다.
   넣으려면 세트로 넣어야 합니다.

**1차 처리 방침:**

| 경로 | 처리 |
|------|------|
| `alert/rule/query/datasource.go` `RenderQuery()` | `GetQuery()` 유지 (pongo2) |
| `alert/handler.go:768` 쿼리 테스트 경로 | `GetQuery()` 유지 (pongo2) |
| Alert 등록/수정 UI | templateStyle switch 미추가 |

### 2차 구현 시 고려사항

Alert에 Grafana 스타일을 추가할 경우 아래 항목을 세트로 설계해야 합니다.
부분 구현은 저장-실행 불일치를 유발하므로 하나만 넣으면 안 됩니다.

**1. Alert rule 저장 포맷 변경 (JSON payload 계약 변경, DB 컬럼 추가 아님)**

`alert_rule.rule` 컬럼은 JSON 문자열 그대로 저장됩니다.
DB 스키마(컬럼) 변경은 없고, 그 JSON의 내부 계약이 바뀌는 것입니다.
기존 row는 `template_style` 없음 → 백엔드 fallback `"pongo2"` 처리로 하위 호환합니다.

`Datasource` 구조체에 `TemplateStyle` 추가:
```go
type Datasource struct {
    Variables     map[string]any `json:"variables,omitempty"`
    Query         string         `json:"query"`
    TimeLabel     string         `json:"time_label"`
    VariableLabel string         `json:"variable_label"`
    TemplateStyle string         `json:"template_style,omitempty"` // 신규 (없으면 "pongo2" fallback)
}
```

**네이밍 규칙: snake_case vs camelCase 분리**

alert 쪽은 저장 포맷과 API 요청 포맷의 네이밍이 다릅니다.
dashboard와 동일한 규칙을 따릅니다.

| 레이어 | 필드명 | 예시 |
|--------|--------|------|
| alert rule 저장 JSON | `template_style` | `"template_style": "grafana"` |
| API 요청 body | `templateStyle` | `"templateStyle": "grafana"` |
| Go 구조체 | `TemplateStyle` | `TemplateStyle string` |

`APIAdapter.FromAPIQueryRequest()`에서 camelCase → snake_case 매핑을 처리합니다.

**2. 스케줄러 실행 경로 교체**

```go
// 현재
func (d Datasource) RenderQuery() ([]byte, error) {
    return alert_common.GetQuery(d.Query, d.Variables)
}

// 변경 후
func (d Datasource) RenderQuery() ([]byte, error) {
    return query_builder.Build(
        query_builder.Style(d.TemplateStyle),
        d.Query,
        d.Variables,
    )
}
```

**3. Alert 전용 static variables 설계**

대시보드는 사용자가 화면에서 변수를 선택합니다.
Alert는 백그라운드 실행이므로 변수를 rule 등록 시 정적으로 지정하는 구조가 필요합니다.

예시 (alert rule JSON 확장):
```json
{
  "datasource": "prometheus",
  "datasource_query": {
    "query": "up{job=~\"$job\"}",
    "variables": {
      "job": "production"
    },
    "template_style": "grafana",
    "time_label": "timestamp",
    "variable_label": "value"
  }
}
```

단, 이 방식은 변수 값이 rule 등록 시점에 고정됩니다.
동적 변수가 필요한 경우(예: 현재 시간 기준 범위) 별도 매크로 지원이 필요합니다.

**4. Alert rule 등록 UI 수정**

| 추가 항목 | 내용 |
|----------|------|
| `grafanaStyle` switch | query별 템플릿 스타일 선택 |
| Static variables 편집 | key-value 형태로 변수 정적 등록 |

현재 UI에 없는 개념이므로 화면 설계부터 시작해야 합니다.

**5. Preview(테스트) 경로 전체 전파**

Alert preview 경로는 단순히 `handler.go`만 바꾸면 안 됩니다.
`API → adapter → internal spec → handler` 전 구간에 `TemplateStyle`이 흘러야 합니다.

현재 preview 흐름:
```
AlertQueryRequest
  └─ APIAdapter.FromAPIQueryRequest()
       └─ resources.Query (= query_builder.Query)
            └─ QuerySpec { Query, Variables, TimeLabel, VariableLabel }
                 └─ handler.go:768 → GetQuery()
```

변경 후 흐름:
```
AlertQueryRequest (templateStyle 추가)
  └─ APIAdapter.FromAPIQueryRequest() (templateStyle 매핑 추가)
       └─ resources.Query (= query_builder.Query)
            └─ QuerySpec { Query, Variables, TimeLabel, VariableLabel, TemplateStyle } ← 신규
                 └─ handler.go:768 → Build(style, query, variables)
```

수정 대상:

| 파일 | 수정 내용 |
|------|---------|
| `shared/types/alert/` alert schema | `AlertQueryRequest.query`에 `templateStyle` 필드 추가 |
| `core/internal/query_builder/query_spec.go` | `QuerySpec`에 `TemplateStyle string` 추가 |
| `core/pkg/alert/adapters/api_adapter.go` | `FromAPIQueryRequest()`에서 `api.Query.TemplateStyle` → `internal.Query.Query.TemplateStyle` 매핑 |
| `core/pkg/alert/handler.go:768` | `GetQuery()` → `Build(style, query, variables)` 교체 |

`resources.QuerySpec`과 `resources.Query`는 `query_builder` 패키지의 type alias이므로
`QuerySpec`에 `TemplateStyle`을 추가하면 자동으로 반영됩니다.

```go
// query_spec.go 변경 후
type QuerySpec struct {
    Variables     map[string]any `json:"variables" mapstructure:"variables"`
    Query         string         `json:"query" mapstructure:"query"`
    TimeLabel     string         `json:"time_label" mapstructure:"time_label"`
    VariableLabel string         `json:"variable_label" mapstructure:"variable_label"`
    TemplateStyle string         `json:"template_style" mapstructure:"template_style"` // 신규
}

// api_adapter.go FromAPIQueryRequest() 변경 후
func (a *APIAdapter) FromAPIQueryRequest(api alert.AlertQueryRequest) *resources.Query {
    return &resources.Query{
        Datasource: api.Datasource,
        Query: resources.QuerySpec{
            Query:         api.Query.Query,
            Variables:     api.Query.Variables,
            TemplateStyle: api.Query.TemplateStyle, // 신규 매핑
        },
    }
}

// handler.go:768 변경 후
queryResp, err := query_builder.Build(
    query_builder.Style(res.Query.Query.TemplateStyle),
    res.Query.Query.Query,
    res.Query.Query.Variables,
)
```

**핵심: preview와 scheduler가 동일한 `TemplateStyle`로 실행되어야 합니다.**
preview만 Grafana 스타일로 바꾸고 scheduler는 pongo2로 두면
등록 전 테스트는 성공하는데 실제 alert 실행 결과가 달라지는 문제가 생깁니다.

## 11. 1차 개발 미결 사항 (2026-05-21)

1차 구현 전에 정책을 확정하거나 코드를 추가로 확인해야 하는 항목들입니다.

### [정책 결정 필요] A. `$__step` / `$__interval` / `$__interval_ms` 처리 여부

Pharos는 Prometheus QueryRange 실행 시 `__step`을 context에서 추출합니다.

```go
// query.go:197
step, ok3 := toInt64("__step")
```

Grafana의 `$__interval` / `$__interval_ms`는 Pharos의 `__step`과 유사한 개념입니다.

**핵심 관점: 백엔드 alias 불필요, 프론트 variables 주입으로 해결 가능**

context whitelist 정책상 프론트엔드에서 variables 맵에 원하는 이름으로 값을 넣으면
백엔드 빌더는 자동으로 치환합니다. 특별한 alias 처리가 필요 없습니다.

```typescript
// 프론트엔드에서 variables 맵에 추가
const variables = {
  __start_time: startTime,
  __end_time:   endTime,
  __step:        stepSeconds,           // 기존 (초 단위 확인 후)
  __interval:    `${stepSeconds}s`,     // 추가: Grafana $__interval 호환
  __interval_ms: stepSeconds * 1000,    // 추가: Grafana $__interval_ms 호환
};
```

이렇게 하면 `$__interval` → `ctx["__interval"]` = `"30s"` → 자동 치환됩니다.
`$__interval_ms` → `ctx["__interval_ms"]` = `30000` → 마찬가지로 자동 치환됩니다.

**단, 단위 확인 필요:**

| 변수 | 타입 | 예시 |
|------|------|------|
| Grafana `$__interval` | duration 문자열 | `"30s"` |
| Grafana `$__interval_ms` | 숫자 (밀리초) | `30000` |
| Pharos `__step` | 숫자 (단위 코드 확인 필요) | `30` or `30000` |

Pharos `__step`이 초 단위인지 확인 후 `__interval` 변환 포맷을 결정합니다.

**선택지:**

| 선택 | 처리 방식 | 변경 위치 |
|------|----------|---------|
| A) 지원 안 함 | context 없음 → 원본 유지 (빌더 오류 없음, 실행 오류 가능) | 없음 |
| B) 프론트 variables 주입 | `__interval: \`${stepSeconds}s\``, `__interval_ms: stepSeconds * 1000` 를 variables에 추가 | 프론트엔드만 |
| C) 백엔드 alias | `replaceTimeAliases()`에 `$__interval` / `$__interval_ms` → `ctx["__step"]` 기반 매핑 추가 | 백엔드만 |

B가 가장 단순하고 백엔드 변경이 없어 권장합니다.
단위만 확인되면 프론트 variables 맵 확장으로 즉시 해결됩니다.

---

### [정책 결정 필요] B. `[[var:format]]` 레거시 문법 format 지원 여부

Grafana 정규식은 레거시 문법에서도 format을 캡처합니다.

```
\[\[(\w+?)(?::(\w+))?\]\]
      ↑          ↑
   varName     format (optional)
```

`[[hosts:csv]]` → varName=`hosts`, format=`csv`

**선택지:**

| 선택 | 처리 |
|------|------|
| A) format 미지원 | `[[hosts:csv]]` → format 무시, 값만 치환 |
| B) format 지원 | `[[hosts:csv]]` → `${hosts:csv}`와 동일하게 처리 |

format을 무시할 경우 사용자가 `[[hosts:csv]]`를 쓰면 예상과 다른 결과가 나옵니다.
지원하는 것이 일관성 있지만 설계서에 명시되지 않았습니다.

---

### [구현 명세 필요] C. 단일값 / 다중값 판별 로직

`formatGrafanaVariable(val any, format string)` 함수 내부에서
`val`이 단일값인지 다중값인지에 따라 출력이 달라집니다.

| format | 단일값 (`"job1"`) | 다중값 (`["job1","job2"]`) |
|--------|-----------------|--------------------------|
| glob (미지정) | `job1` | `{job1,job2}` |
| csv | `job1` | `job1,job2` |
| regex | `job1` | `(job1|job2)` |
| json | `"job1"` | `["job1","job2"]` |
| singlequote | `'job1'` | `'job1','job2'` |
| sqlstring | `'job1'` | `'job1','job2'` |

Go에서 `ctx map[string]any`의 값은 JSON 역직렬화 시 아래 타입으로 들어옵니다.

```go
// 단일값: string
// 다중값: []any (JSON array → []interface{})

func formatGrafanaVariable(val any, format string) string {
    switch v := val.(type) {
    case string:
        return formatSingle(v, format)
    case []any:
        strs := toStringSlice(v)
        return formatMulti(strs, format)
    default:
        return fmt.Sprintf("%v", val) // number 등 fallback
    }
}
```

이 판별 로직을 `grafana.go` 구현 전에 명세로 확정해야 합니다.

```go
        return GetQuery(query, ctx)

}
```

### 자동 감지 판별 기준

기존 코드베이스 전체가 datasource 이름에 `"prometheus"` 포함 여부로 판별하고 있다.

```
core/frontend/src/features/dashboard/hooks/QueryPipeline.ts:286

core/frontend/src/features/dashboard/panels/components/PanelEditor/left-bottom.tsx:38
```

최종 확정된 헬퍼는 아래와 같다 (섹션 12 "type 기반 감지 헬퍼" 참고):

```typescript
const isPrometheusDatasource = (name: string, type?: string): boolean =>
  type
    ? type.toLowerCase() === 'prometheus'
    : name.toLowerCase().includes('prometheus');
```

선택된 datasource 조회:

### validateQuery 분기

**현재 (문제):**
```typescript
const validateQuery = (query: string): QueryValidationResult => {
  if (!queryLower.startsWith('select')) {
    return { isValid: false, message: 'Query must be a SELECT statement' };
  }
  // ...
};
```
datasource 무관하게 SELECT 강제 → Prometheus 쿼리 전부 빨간 에러.

**변경 후:**
```typescript
const validateQuery = (query: string, isPrometheus: boolean): QueryValidationResult => {
  if (!query.trim()) {
    return { isValid: true, message: '' };
  }

  // Prometheus datasource는 PromQL / Grafana classic variable query 허용
  if (isPrometheus) {
    return { isValid: true, message: '' };
  }

  // SQL datasource: SELECT + value/label 컬럼 검사
  const queryLower = query.toLowerCase().trim();
  if (!queryLower.startsWith('select')) {
    return { isValid: false, message: 'Query must be a SELECT statement' };
  }
  const hasValue = queryLower.includes('as value') || queryLower.includes(' value,') || queryLower.includes(' value ');
  const hasLabel = queryLower.includes('as label') || queryLower.includes(' label,') || queryLower.includes(' label ');
  if (!hasValue || !hasLabel) {
    return {
      isValid: false,
      message: 'Query must include "value" and "label" columns (e.g., "column_name AS value, column_name AS label")',
    };
  }

  return { isValid: true, message: '' };
};
```

호출부도 동일하게 `isPrometheus`를 넘겨야 한다:
```typescript
// handleChange 내부
const validation = validateQuery(value, isPrometheus);

// useEffect 내부 (datasource 변경 시 재검증)
useEffect(() => {
  if (data.query) {
    setQueryValidation(validateQuery(data.query, isPrometheus));
  }
}, [data.query, isPrometheus]);
```

datasource가 바뀌면 `isPrometheus` 값이 변하고 `useEffect`가 재실행되어 자동으로 재검증된다.

### 가이드 텍스트 분기

SQL datasource일 때 현재 안내 텍스트를 유지하고,
Prometheus datasource일 때는 아래로 교체한다.

**Prometheus 안내 (isPrometheus = true):**
```
Write a PromQL or Grafana classic variable query:

• PromQL: label_replace(...), vector(0), up{job=~"$job"}
• Grafana classic: label_values(metric, label_name)
                   label_values(metric{job=~"$job"}, label_name)

Example:
  label_values(up{job=~"$job"}, instance)
  → Shows "instance" label values from metrics where job matches $job

Variable references: use $varName or ${varName} syntax.
Note: query_result() is not yet supported.
```

**SQL 안내 (isPrometheus = false, 현재 유지):**
```
Write a SELECT query that returns "value" and "label" columns:
  ...
Example: SELECT system_id AS value, system_name AS label FROM table_name ...
```

placeholder도 분기한다:
- SQL: `SELECT column_name AS value, column_name AS label FROM table_name`
- Prometheus: `label_values(metric, label_name)`

### 주의: label_values 실행 어댑터는 별도 작업

`validateQuery` 분기와 가이드 텍스트 변경, QueryPipeline/DependencyGraph dependency 추출은 모두 프론트 UI 레이어 수정이다.
실제로 `label_values(metric, label_name)` 쿼리를 실행하면 Prometheus가 해당 함수를
PromQL 함수로 인식하지 못해 오류를 반환하므로, 실행 어댑터는 별도 작업이 필요하다.

작업 순서:
1. **이번**: `QueryFields` validation + 가이드 텍스트, `QueryPipeline` + `DependencyGraph` dependency 추출 분기
2. **다음**: 어댑터에서 `label_values(...)` 파싱 → Prometheus API 변환
   - `query_result()`는 어댑터 구현 전까지 미지원 (안내 텍스트에서 제외)
   - **중요**: `label_values(up{job=~"$job"}, instance)` 형태는 API 호출 전에 `$job`을 실제 값으로 치환해야 한다.
     FilterConfig에 templateStyle을 추가하지 않으므로 어댑터가 직접 `extractGrafanaVariables()`로 변수를 식별하고 치환한다.
     치환 데이터 소스는 구현 위치에 따라 다르다:
     - **프론트 어댑터**: filterMetas에서 현재 선택값을 조회해 `$job` → 실제 값으로 치환 후 Prometheus API 호출
     - **백엔드 어댑터**: 이미 resolve된 `variables` map(`{"job": "tcp-bridge", ...}`)으로 `$job` 치환 후 Prometheus API 호출
   - **Prometheus API 호출 방식**: 인자 구성에 따라 3가지로 분기

     | 쿼리 형태 | Prometheus API |
     |----------|---------------|
     | `label_values(pod)` — label만 | `GET /api/v1/label/pod/values` |
     | `label_values(up, pod)` — metric + label | `GET /api/v1/label/pod/values?match[]=up` |
     | `label_values(up{job=~"tcp-bridge"}, pod)` — metric + selector + label | `GET /api/v1/label/pod/values?match[]=up{job=~"tcp-bridge"}` |

     metric이 있으면 항상 `match[]`를 붙여야 한다. 생략하면 metric 필터가 무시되어 전체 label 값이 반환된다.
     `match[]`로 원하는 결과가 나오지 않는 경우 `/api/v1/series?match[]=...` 후 해당 label 값을 추출하는 방식도 가능하다.

   - **파싱 주의 — 최상위 comma 기준 인자 분리:**
     `label_values(up{job=~"$job", instance=~"$instance"}, pod)` 처럼
     selector 내부에도 comma가 들어간다. 단순 `split(',')` 로 구현하면 인자 분리가 깨진다.
     먼저 `label_values(` prefix와 마지막 `)`를 제거한 뒤, 내부 인자 문자열에서
     괄호/중괄호 depth가 0이고 quoted string 바깥인 comma만 인자 구분자로 사용해야 한다:
     ```
     inner: up{job=~"$job", instance=~"$instance"}, pod
                              ↑ selector 내부 comma이므로 무시
                                                       ↑ depth 0 + quote 바깥이므로 인자 구분자
     ```
     PromQL label matcher 안에는 quoted string이 들어가므로 quote/escape 상태도 함께 추적한다.
     예를 들어 `"..."` 안의 comma, `{`, `}`는 depth 계산과 인자 분리에 영향을 주면 안 되고,
     `\"`, `\\` 같은 escape sequence는 quote 종료로 오인하지 않아야 한다.

   - **`match[]` URL 인코딩 주의:**
     `match[]` 값은 URL query parameter이므로 HTTP 클라이언트에서 query param으로 설정해 자동 인코딩되게 해야 한다.
     문자열 직접 concatenation으로 URL을 만들면 `{`, `}`, `=~` 등이 인코딩되지 않아 Prometheus가 파싱 오류를 낼 수 있다.

## 0. Recent Update - label_values() dependency fallback (2026-05-22)

### Context

Observed log:

```text
rawQuery:      label_values(tcp_bridge:ready_connection_state:max{job=~"$job", pod=~"$pod"}, sys_id)
```

The issue shown by this log is not string interpolation itself. It is that the `pod` variable value was still empty when the `sys_id` variable query ran.

For this query:

```promql
label_values(tcp_bridge:ready_connection_state:max{job=~"$job", pod=~"$pod"}, sys_id)
```

the expected cascade is:

```text
job -> pod -> sys_id
```

`sys_id` should not re-run the `pod` query and use the full option list. It should use the current selected value of the already executed `pod` variable.

If the `pod` variable is set to All, the value should be the configured custom all value, normally:

```promql
pod=~".*"
```

Existing design used Grafana variable extraction when the datasource is detected as Prometheus:

```typescript
extractVariables(query) + extractGrafanaVariables(query)
```

That is still correct, but datasource detection can be late or unavailable in some paths, especially when `datasourceType` has not yet been injected or viewer responses hide `filters[].datasourceName` / `filters[].query`.

```typescript
export function isGrafanaClassicVariableQuery(query: string): boolean {

}
```

```typescript
const needsGrafanaExtract =
  isPrometheusDatasource(datasourceName, datasourceType) ||
```

## 0-A. Runtime default value fallback for multi-value All variables (2026-05-22)

### Decision

When a downstream query references `$pod`, do not re-run the `pod` variable query just to fill the missing value.
Use the variable configuration's default policy instead.

The chosen fallback is:

```text
if $pod is required
and pod.value is empty
and pod.options.showAllOption === true
and pod.options.defaultAllSelected === true
and pod.options.customAllValue is not empty
then set pod.value = [pod.options.customAllValue]
```

For the current Prometheus variable case this means:

```text
pod.value = [".*"]
```

and the downstream `sys_id` query should receive:

```promql
pod=~".*"
```

### Why this is preferred

The alternative idea was to inspect `$pod`, find the `pod` variable definition, execute the `pod` label query again, and use the returned label values.
That is technically possible, but it is not the desired runtime model.

Reasons:

- Variable query results are option lists, not selected values.
- Re-running the label query from the downstream variable duplicates requests.
- It can diverge from what the user sees in the select box.
- It complicates cycle handling (`a` depends on `$b`, `b` depends on `$a`).

The cleaner model is:

```text
variable query result -> option list
variable config/default policy -> selected runtime value
downstream query -> uses selected runtime value
```

So when `pod` is configured as:

```text
Enable multi-select: true
Show "All" option: true
Default to "All" selected: true
Custom "All" value: .*
```

the runtime store should initialize `pod.value` to:

```typescript
['.*']
```

without waiting for a manual select-box action.

### Implementation target

This fallback belongs in the frontend runtime variable layer, not in the backend query builder.

Candidate locations:

- `useDashboardQuery.ts`: after variable query success, before marking dependent variables ready
- `variable-runtime-slice.ts`: inside `setFilterMeta()` or a small helper that applies default values
- `SelectVariable.tsx`: when the variable config clearly requests default All and the current value is empty

Recommended direction:

Use a shared helper so both initial load and later cascade refresh use the same rule.

Pseudo-code:

```typescript
function getDefaultRuntimeValue(metaOrConfig) {
  const options = metaOrConfig.options;
  if (
    options?.isMulti === true &&
    options?.showAllOption === true &&
    options?.defaultAllSelected === true &&
    options?.customAllValue
  ) {
    return [options.customAllValue];
  }
  return undefined;
}
```

Then, when a variable is required but has no value:

```typescript
const defaultValue = getDefaultRuntimeValue(meta);
if (defaultValue !== undefined) {
  setFilter(variableId, defaultValue);
}
```

### Important distinction

This fallback should only set the **selected runtime value**.
It should not replace the query result option list.

For example, the `pod` select box may still display:

```text
All
tcp-bridge-0-857d58f65c-fvv7z
tcp-bridge-1-748579d9-hwp9t
```

but the store value used by `$pod` should be:

```typescript
['.*']
```

unless the user explicitly selects a concrete pod value.

### Expected result

With this fallback, the saved variable query can stay dynamic:

```promql
label_values(tcp_bridge:ready_connection_state:max{job=~"$job", pod=~"$pod"}, sys_id)
```

and when `pod` has no explicit selection but is configured as default All, `sys_id` should execute as:

```promql
label_values(tcp_bridge:ready_connection_state:max{job=~"tcp-bridge", pod=~".*"}, sys_id)
```

instead of:

```promql
label_values(tcp_bridge:ready_connection_state:max{job=~"tcp-bridge", pod=~""}, sys_id)
```

## 0-B. Grafana `$__rate_interval` 지원 설계 (2026-05-26)

### 배경

Grafana style PromQL에서 다음과 같은 쿼리를 사용할 수 있다.

```promql
increase(metric[$__rate_interval])
```

현재 Pharos frontend payload에는 대략 다음 variables가 전달된다.

```json
{
  "__interval": "30s",
  "__interval_ms": 30000,
  "__step": 30,
  "__start_time": 1779780294,
  "__end_time": 1779783894,
  "__start_time_ms": 1779780294887,
  "__end_time_ms": 1779783894887,
  "job": "tcp-bridge",
  "pod": ".*",
  "sys_id": ".*"
}
```

하지만 `__rate_interval`과 `__rate_interval_ms`는 없다.

현재 `buildGrafana()`는 context에 없는 Grafana variable을 원문 그대로 유지한다.

```go
if !exists {
    return match
}
```

따라서 `$__rate_interval`이 치환되지 않고 Prometheus로 전달될 수 있고, 이 경우 다음과 같은 오류가 발생한다.

```text
bad_response: struct Decode: expect }, but found ",
parse error: bad number or duration syntax
```

### Grafana 공식

Grafana의 `$__rate_interval` 계산식은 다음과 같다.

```text
$__rate_interval = max($__interval + scrape_interval, 4 * scrape_interval)
```

예시:

```text
__interval = 30s
scrape_interval = 15s

max(30s + 15s, 4 * 15s)
= max(45s, 60s)
= 60s
= 1m
```

따라서 현재 payload 기준에서 scrape interval fallback을 `15s`로 잡으면 기대값은 다음과 같다.

```json
{
  "__rate_interval": "1m",
  "__rate_interval_ms": 60000
}
```

### scrape interval 정책

Grafana가 Prometheus 서버에서 실제 scrape interval을 자동 조회하는 것은 아니다.

Grafana는 사실상 다음 우선순위로 scrape interval을 결정한다.

1. Query option의 `Min step`이 있으면 그 값을 사용
2. 없으면 Prometheus datasource 설정의 `Scrape interval` 사용
3. 그것도 없으면 일반적으로 `15s` fallback

현재 Pharos payload에는 datasource scrape interval이 없다.

권장 정책:

```text
scrape_interval = context["__scrape_interval"]이 있고 유효하면 그 값 사용
scrape_interval = 없거나 유효하지 않으면 15s fallback
```

`__scrape_interval`은 지금 당장 frontend가 보내지 않아도 되는 예약 확장 변수로 둔다.
나중에 datasource 설정에 scrape interval이 추가되면 variables map에 다음 값을 넣어주면 된다.

```json
{
  "__scrape_interval": "15s"
}
```

### 구현 위치

권장 구현 위치:

```text
core/internal/query_builder/grafana.go
```

이유:

- `$__rate_interval`은 Grafana style 전용 built-in variable이다.
- `$__from`, `$__to`도 현재 `grafana.go`에서 pre-processing으로 처리한다.
- Backend에서 처리하면 panel 실행, 직접 Run Query, Query Inspect 경로가 일관된다.
- Frontend에만 넣으면 실행 경로별로 중복되거나 누락될 수 있다.

현재 흐름:

```text
buildGrafana(query, queryContext)
  -> convertInternalContext(queryContext)
  -> replaceGrafanaTimeAliases()
  -> grafanaVariablePattern.ReplaceAllStringFunc()
```

권장 흐름:

```text
buildGrafana(query, queryContext)
  -> convertInternalContext(queryContext)
  -> enrichGrafanaBuiltins()
       - __rate_interval 없으면 추가
       - __rate_interval_ms 없으면 추가
       - __scrape_interval 있으면 우선 사용
       - 없으면 15s fallback
  -> replaceGrafanaTimeAliases()
  -> grafanaVariablePattern.ReplaceAllStringFunc()
```

`enrichGrafanaBuiltins()`와 `replaceGrafanaTimeAliases()`의 순서는 현재 기능상 큰 차이가 없다.
단, Grafana variable replacement 전에 `__rate_interval`이 context에 들어가 있어야 한다.

### 명시 값 보존

Backend fallback은 명시적으로 전달된 값을 덮어쓰지 않는다.

정책:

```text
context["__rate_interval"]이 이미 있으면 유지한다.
context["__rate_interval_ms"]가 이미 있으면 유지한다.
없는 값만 계산해서 추가한다.
```

권장 보완:

```text
__rate_interval은 있고 __rate_interval_ms가 없으면:
  __rate_interval을 parsePromDuration()으로 파싱해서 __rate_interval_ms를 추가한다.

__rate_interval_ms는 있고 __rate_interval이 없으면:
  __rate_interval_ms를 duration으로 변환한 뒤 __rate_interval을 추가한다.
```

### `enrichGrafanaBuiltins()` 설계

역할:

- Grafana context map에 backend에서 계산 가능한 built-in variable을 보강한다.
- 초기 대상은 `$__rate_interval`과 `$__rate_interval_ms`이다.

권장 동작:

```text
1. context가 nil이면 초기화한다.
2. __interval을 parsePromDuration()으로 파싱한다.
3. __interval이 없거나 유효하지 않으면 interval = 0으로 처리한다.
4. __scrape_interval을 parsePromDuration()으로 파싱한다.
5. __scrape_interval이 없거나 유효하지 않으면 scrape = 15s로 처리한다.
6. rate = max(interval + scrape, 4 * scrape)를 계산한다.
7. __rate_interval이 없으면 formatPromDuration(rate)로 추가한다.
8. __rate_interval_ms가 없으면 rate.Milliseconds()로 추가한다.
9. 이미 존재하는 명시 값은 덮어쓰지 않는다.
```

의사 코드:

```go
func enrichGrafanaBuiltins(context map[string]any) map[string]any {
    if context == nil {
        context = map[string]any{}
    }

    interval, ok := parsePromDuration(context["__interval"])
    if !ok {
        interval = 0
    }

    scrape, ok := parsePromDuration(context["__scrape_interval"])
    if !ok {
        scrape = 15 * time.Second
    }

    rate := interval + scrape
    minRate := 4 * scrape
    if rate < minRate {
        rate = minRate
    }

    if _, exists := context["__rate_interval"]; !exists {
        context["__rate_interval"] = formatPromDuration(rate)
    }

    if _, exists := context["__rate_interval_ms"]; !exists {
        context["__rate_interval_ms"] = rate.Milliseconds()
    }

    return context
}
```

### `parsePromDuration()` 설계

역할:

- Prometheus/Grafana duration 값을 `time.Duration`으로 파싱한다.
- 문자열과 숫자 값을 모두 지원한다.

지원해야 하는 입력:

```text
"30s"   -> 30s
"1m"    -> 1m
"5m30s" -> 5m30s
"1h"    -> 1h
"1d"    -> 24h
"7d"    -> 168h
"1w"    -> 168h
30      -> 30s
30.0    -> 30s
```

중요:

- Go `time.ParseDuration()`은 `s`, `m`, `h`를 지원한다.
- Go `time.ParseDuration()`은 `d`, `w`를 지원하지 않는다.
- PromQL duration에서는 `d`, `w`가 현실적으로 등장할 수 있다.
- 따라서 커스텀 파서가 권장된다.

권장 지원 단위:

```text
ms, s, m, h, d, w
```

`y` 지원은 선택 사항이다. 초기 `$__rate_interval` 구현에는 필수는 아니다.

숫자 scalar 값은 초 단위로 해석한다.

```text
parsePromDuration(15)    -> 15s
parsePromDuration("15s") -> 15s
```

### `formatPromDuration()` 설계

역할:

- 계산된 duration을 PromQL range selector에 넣기 좋은 compact 문자열로 포맷한다.

Go `time.Duration.String()`은 `1m0s` 같은 문자열을 만들 수 있다.
PromQL에서 동작할 수는 있지만 Grafana style 출력으로는 `1m`이 더 자연스럽다.
따라서 명시적인 compact formatter를 둔다.

기대 출력:

```text
45s     -> "45s"
60s     -> "1m"
90s     -> "1m30s"
3600s   -> "1h"
3660s   -> "1h1m"
86400s  -> "1d"
86415s  -> "1d15s"
604800s -> "1w"
```

권장 단위 우선순위:

```text
w, d, h, m, s
```

`$__rate_interval` 용도로는 millisecond 출력이 필수는 아니다.
계산 결과가 1초보다 작으면 `1s`로 올림 또는 clamp 처리하는 것을 권장한다.

이유:

```text
rate(metric[0s])
```

같은 값은 실사용 의미가 없다.
또한 scrape fallback이 `15s`이면 정상 경로에서는 1초 미만 값이 나오지 않는다.

### `__interval`이 없을 때

`__interval`이 없거나 유효하지 않으면:

```text
interval = 0
```

공식:

```text
rate = max(0 + scrape, 4 * scrape)
     = 4 * scrape
```

scrape fallback이 `15s`이면:

```text
rate = 60s = 1m
```

따라서 `__interval`이 없을 때 기본 `$__rate_interval`은 `1m`이다.
이 동작은 코드 주석과 테스트에 명시한다.

## 0-C. TimeSeries Legend의 `msg_type` hex 문자열 처리 수정 정리 (2026-05-26)

### 배경

TimeSeries 패널에서 Legend rule을 아래처럼 설정했다.

```text
{msg_type} {reason}
```

쿼리는 아래 형태였다.

```promql
sum by (msg_type, reason) (
  increase(tcp_bridge_inbound_outcomes_total{job=~"$job", pod=~"$pod", reason!="ok"}[$__rate_interval])
)
```

백엔드 응답에는 `msg_type`, `reason`, `value`가 모두 포함되어 있었다.

예:

```json
{
  "msg_type": "0x0f",
  "reason": "nats_request_failed",
  "timestamp": "2026-05-26T08:49:00Z",
  "value": "0"
}
```

그런데 화면의 legend는 설정한 `{msg_type} {reason}` 형식이 아니라 `reason=nats_request_failed`처럼 출력되었다.

### 원인

프론트엔드의 차트 데이터 변환 로직이 문자열 값을 숫자로 분류할 때 JavaScript `Number()` 변환을 사용하고 있었다.

기존 로직:

```ts
typeof value === 'string' && !isNaN(Number(value)) && value !== ''
```

JavaScript에서는 아래 변환이 유효하다.

```ts
Number("0x0f") === 15
```

따라서 Prometheus label 값인 `"0x0f"`가 문자열 label이 아니라 numeric field로 잘못 분류되었다.

결과적으로 내부 데이터는 대략 아래처럼 만들어졌다.

```text
numericFields:
  msg_type = 15
  value = 0

stringFields:
  reason = nats_request_failed
```

TimeSeries legend label은 `stringFields`를 기준으로 metric label을 구성한다.

따라서 `msg_type`이 metric label에서 빠졌고, Legend rule의 `{msg_type}` placeholder가 치환되지 않았다.

`formatLegendLabel()`은 치환 후에도 `{...}` placeholder가 남아 있으면 custom rule 적용 실패로 보고 기본 포맷으로 fallback한다.

그래서 최종 출력이 아래처럼 보였다.

```text
reason=nats_request_failed
```

### 수정 방향

문자열 숫자 판별을 `Number()`의 느슨한 변환에 의존하지 않도록 변경했다.

`0x0f` 같은 hex 문자열은 Prometheus label로 유지되어야 하므로 numeric field로 분류하지 않는다.

대신 일반 decimal 숫자 문자열만 numeric field로 인정한다.

허용 예:

```text
0
12
-12
12.3
.5
1e-3
```

비허용 예:

```text
0x0f
0xff
nats_request_failed
normal
```

### 구현 내용

수정 파일:

```text

```

추가된 헬퍼:

```ts

const isNumericString = (value: string): boolean => numericStringPattern.test(value.trim());
```

변경 전:

```ts
} else if (typeof value === 'string' && !isNaN(Number(value)) && value !== '') {
  numericFields[key] = Number(value);
}
```

변경 후:

```ts

  numericFields[key] = Number(value);
}
```

### 기대 동작

응답:

```json

  "msg_type": "0x0f",
  "reason": "nats_request_failed",
  "value": "0"
}
```

변환 후 기대 구조:

```text

  value = 0

stringFields:
  msg_type = 0x0f
  reason = nats_request_failed
```

Legend rule:

```text

```

기대 출력:

```text

```

## 0-D. Grafana `$__rate_interval` 기본 scrape interval 30s 정렬 (2026-05-27)

### 배경

Grafana Query Inspector에서 같은 tcp-bridge inbound outcome 쿼리가 아래처럼 실행되는 것을 확인했다.

```text
increase(tcp_bridge_inbound_outcomes_total{...}[2m0s])
Step: 30s
```

패널 Query options에는 다음 값이 있었다.

```text
Min interval = 30s
Interval     = 30s
```

Pharos inspect payload도 `__interval`과 `__step`은 Grafana와 동일하게 30초였다.

```json
{
  "__interval": "30s",
  "__interval_ms": 30000,
  "__step": 30
}
```

하지만 Pharos에는 Prometheus datasource의 scrape interval 또는 Grafana panel min step에 해당하는 값이
`__scrape_interval`로 전달되지 않았다.

기존 Pharos backend fallback은 15초였으므로:

```text
$__rate_interval = max(30s + 15s, 4 * 15s)
                 = max(45s, 60s)
                 = 1m
```

Grafana는 30초 min step/scrape 기준으로 계산되어:

```text
$__rate_interval = max(30s + 30s, 4 * 30s)
                 = max(60s, 120s)
                 = 2m
```

따라서 Grafana style 쿼리에서는 `[1m]`, pong2 또는 Grafana Inspector에서는 `[2m]`가 되어
결과 series 수가 40개와 80개로 달라질 수 있었다.

### 결정

현재 Pharos는 Grafana panel의 Prometheus query min step을 별도 UI/설정으로 관리하지 않는다.
또한 해당 Grafana style 동작은 Prometheus 쿼리에서만 의미가 있다.

따라서 datasource 설정을 새로 추가하기 전에, Pharos Grafana style의 기본 Prometheus scrape interval fallback을
15초에서 30초로 변경했다.

```text
defaultGrafanaScrapeInterval = 30s
```

이 결정은 쿼리마다 `[2m]`를 직접 박는 방식보다 `$__rate_interval` 사용을 유지하면서 Grafana와 결과를 맞추기 위한 것이다.

### 수정 파일

